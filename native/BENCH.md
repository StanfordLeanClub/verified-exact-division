# BENCH — array / scalar: exact mul+FMA kernels vs vdivpd/vdivps (Intel Core Ultra 7 155U)

These are measured wall-clock throughputs on one laptop. They are not operation counts and they are not proofs.

**Semantics.** Each kernel returns the same value as `x / y` for every element. NaN in gives NaN out, but the sign
and payload of the NaN are not guaranteed to match hardware division. In the tests, NaN results with different bits
are counted separately and are not counted as mismatches:
- P1, P2, P3 and the P4 same-sign branch reproduce the NaN bits of `vdivpd` on x86. Their special-lane value is
  `x * zh`.
- The P4 opposite-sign branch can set the sign bit of a NaN.
- P3X (the old `x ^ signbit(y)` special value) flips the NaN sign when y < 0.

**Correctness**
- `results/native_kernels_p4.txt`: all policies, part A plus exhaustive float32 part B. 8.76e11 elements, 0
  mismatches.
- `results/native_kernels_p4_win_partA.txt`: the Windows clang build, part A only.
- `results/native_f64_adversarial.txt`: scalar reference, 2.2e9 comparisons.

The runs below are the **P4 runs of 2026-11-10 12:31–12:40 UTC**. The machine was quiet: the Windows host had
0.10–0.45 busy cores before and after each run (`results/host_load_log.txt`), and the WSL load1 was below 1. The
earlier pre-P4 runs, with the `x ^ signbit(y)` special value and no P3X/P4, are kept in `results/bench_preP4/`.

## Variants

All variants use the same 4-vector unrolling. Each is a `noinline` function called through a function-pointer table.

| variant | per element | exact? |
|---|---|---|
| `div` | `vdivpd`/`vdivps` loop | reference |
| `recip` | `x * (1/y)` | **no**; speed reference |
| `raw` | unguarded `fma(x, zh, x*zl)` | only for tlo <= \|x\| < thi; used only to price the guard |
| `P1` | guard "out of [tlo, thi)"; a flagged block is redone with real division | yes |
| `P2` | the same guard; a flagged block whose flagged lanes are all +-0/+-inf/NaN gets `x*zh` in those lanes (raw q if same_sign), otherwise division | yes |
| `P3` | branchless: blend `x*zh` into special lanes in every block; branch only on finite nonzero lanes outside [tlo, thi) | yes |
| `P3X` | P3 with special value `x ^ signbit(y)` (the former P3) | yes; NaN sign may differ |
| **`P4`** (default) | same_sign and thi = inf → guard "tiny" only (`1 <= 2\|x\| < 2Tlo`), no blend. Opposite sign and thi = inf → guard "tiny or ±inf", zero fix `q \|= x & signmask` (y > 0) or `q \|= ~x & signmask` (y < 0). Finite thi → P3 | yes; NaN sign may differ on the opposite-sign branch |

**Which divisors take which P4 branch.** Same-sign divisors are about half of all FMA-mode divisors.
- binary64: 3 and 255 are same-sign (`efd64_fma_z`); 0.1, √3 and 1e-3 are opposite-sign (`efd64_fma_zfp`).
- binary32: 3, 255 and 0.1 are opposite-sign; 1e-3 is same-sign; (float)√3 is mode DIV.

## Methodology

The method is unchanged from the pre-P4 runs; details are in `results/bench_preP4/BENCH_preP4.md`.

**Timing**
- Variants are sampled interleaved, round-robin within each group: 3 warm-up rounds, then at least 15 rounds (at
  least 31 for n <= 65536).
- Tables give the median ns/element with [min..max]. Timing uses `rdtscp`/`lfence` against a 2.688 GHz TSC.
- The core clock is estimated before and after each group with a dependent `imul` chain.
- Out-of-place: K calls with K*n >= 65536. In-place: K fresh copies with K*n*size >= 16 KiB, refreshed by an untimed
  memcpy.

**Pinning**
- WSL2 has no P/E topology. The WSL run (`taskset -c 2`) ran on a physical core chosen by Windows; its clock median
  was 4.24 GHz, probably a P-core.
- The P/E comparison uses the native Windows build (clang 19.1.5, same flags) pinned with `SetThreadAffinityMask`:
  - logical processor 10, EfficiencyClass 1 (P-core), clock median 4.55 GHz;
  - logical processor 4, EfficiencyClass 0 (E-core), clock median 2.25 GHz.

**Sizes and footprints**
- n = 256, 4096, 65536 is in-cache. f64 n=4096 out-of-place (64 KiB) already exceeds the 48 KiB L1d.
- n = 1 Mi is L3/DRAM. n = 16 Mi is DRAM-bound.

**Replay**
- `native/run_bench.sh 2 wsl_vcpu2 full 15`.
- Windows: `clang -O2 -mavx2 -mfma -ffp-contract=off -D_CRT_SECURE_NO_WARNINGS bench.c -o bench_win.exe`, then
  `set EFD_AFFINITY=10` and `bench_win.exe full <label> 15` and `bench_win.exe setup <label>`.
- `python3 native/summarize.py results/bench_core_ultra_7_155u.json results/bench_raw_*.jsonl > results/bench_tables.md`.
- The kernel header is generated by `native/gen_efd_kernels.py`.

### Reading the data-kind tables

**Same-sign divisors** (f64 y=3, f32 y=1e-3)
- P4 is data-independent. Zeros, NaN, infinities and integers cost nothing. On the P-core f64 at n=4096, every data
  kind runs at 0.140–0.149 ns vs 0.418–0.427 ns for div (2.8–3.0x).
- On normal data P4 is as fast as P2: it has the same uop count, and only the compare constant differs.
- With 10 % zeros, P2 is 5.8x slower (0.823 ns, worse than div). The "below tlo" case still costs a division
  fallback for the block.

**Opposite-sign divisors** (f64 y=0.1, f32 y=3 and y=0.1)
- P4 uses the new zero-fix scheme. It is also flat across data kinds, apart from "below tlo".
- Its fast path costs 4 more uops per vector than P2's (cmpeq + or for ±inf, and + or for the zero sign), so on
  clean data it is 25–70 % slower than P2.
- It beats P3 everywhere. P-core f64: 0.184–0.192 vs 0.234–0.243 ns. E-core f64: 0.54 vs 0.80 ns. f32: 0.09–0.12
  vs 0.12–0.14 ns on the P-core, and 0.27 vs 0.41 ns on the E-core.

**f32 opposite-sign on the P-core is the weak spot.** Division (vdivps) costs only ~0.134 ns per element there.
P4 at 0.092–0.118 ns is just 1.1–1.45x faster. P2 is 2x faster on clean data but collapses with zeros.

## Opposite-sign variants evaluated

**(i) Zero fix, kept.** `q |= x & signmask` (y > 0) or `q |= ~x & signmask` (y < 0), with ±inf flagged by
`vpcmpeqq a, 2*bits(inf)`.
- It is bit-identical as a value in part A and in the exhaustive binary32 part B. Part B covered 40 divisors,
  including −3, −0.1, −255, −1000, −7 and −√3 for the y < 0 form.
- It is faster than P3 in every configuration measured, by 20–35 % P-core and ~33 % E-core. It is the P4
  opposite-sign branch.
- Its NaN outputs can have a different sign bit than vdivpd when y < 0. The counts are in the test output and are
  not mismatches.

**(ii) A pmaxud-style mapping of zero into the range, for 32-bit lanes, was not implemented.**
- Mapping a = 0 to 2Tlo, e.g. `max_u(a, z)` with a constant, would also map the tiny lanes 1..2Tlo−1 into the
  range. Doing it only for a == 0 needs a compare plus a blend or and, which is no cheaper than (i).
- Infinities would still need their own flag, since the raw kernel gives NaN for them.

## Special-lane value: x * zh vs x ^ signbit(y)

- P3 (`x*zh`) and P3X (`x ^ signbit(y)`) are within noise on the P-core.
- On the E-core f32, `x*zh` costs ~3.5 %: 0.408 vs 0.394 ns at n=4096. f64 is equal.
- `x*zh` gives the correctly signed zero and infinity. For a NaN input it returns the quieted input NaN, exactly
  like `vdivpd`/`vdivps`: test_kernels counts 0 NaN-bit differences for P1/P2/P3.
- **Kept: `x*zh`.** P3X remains only as a comparison variant.

## Cost of the guard (P-core, y=3, data i, n=256 out-of-place, in L1)
